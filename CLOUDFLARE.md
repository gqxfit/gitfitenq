# GQX Fit: free Cloudflare hosting

This deployment uses Workers Free, a D1 database, a free workers.dev address and a ten-minute Cron Trigger. No Render service or paid disk is required. Keep the Cloudflare account on its free plan. Free quotas apply; the service can reject requests when quotas are exhausted. WhatsApp Cloud API charges, if enabled, are separate.

## Source and deployment

- `cloudflare-worker.mjs`: API, authentication, D1 outbox, signed inbound webhooks and scheduler.
- `cloudflare-schema.mjs`: D1 tables/indexes; initialized automatically using a transactional batch on first database access.
- `cloudflare-assets.mjs`: public UI assets generated by `node scripts/build-cloudflare.mjs`.
- `wrangler.jsonc`: Worker name, actual D1 ID/binding and ten-minute cron.
- Original Node/SQLite files are retained for local use. Do not point a local SQLite path at D1 or upload the local database to GitHub.

Create a D1 database named `gqx-fit-enquiries` on the Free plan. Put its database UUID in `wrangler.jsonc`. Connect this GitHub repository to a Cloudflare Worker named `gqx-fit-portal`. Set build command `node scripts/build-cloudflare.mjs`, deploy command `npx wrangler deploy`, and disable preview builds to avoid using unnecessary build quota. The Worker name and config name must match. Deploy from `main`.

For local CLI deployment, use an authenticated Wrangler CLI and run `npx wrangler deploy`. Never put Cloudflare API tokens in GitHub source. The connected dashboard build authenticates deployment without committing a token.

## Private admin credentials

To keep login inexpensive within the Free plan CPU limit, hosted admin access uses a cryptographically random 192-bit login key and a SHA-256 verifier. This is a high-entropy credential, **not a user-chosen password hashed with a fast hash**. Do not replace it with a short/memorable password or reuse the Node app's scrypt hash.

Run locally:

```cmd
node scripts/cloudflare-credentials.mjs
```

Open the generated private `.env.cloudflare` file locally. It is ignored by Git and Docker. Save `ADMIN_LOGIN_KEY` in your password manager; enter it into the password field at `/admin`. Add these three **secret** values to the Worker in Cloudflare:

- `ADMIN_KEY_HASH`
- `SESSION_SECRET`
- `CRON_SECRET`

Do not add `ADMIN_LOGIN_KEY` to GitHub or the Worker. Do not send it in chat. The app fails closed for admin login until its required secrets are configured. A credential change needs both a new random key/verifier and a new session secret to revoke prior sessions.

The default `WHATSAPP_ENABLED=false` keeps notifications disabled and records blocked attempts. The portal and persistent enquiries/products work without WhatsApp credentials. Enable WhatsApp only after completing the Meta template, opt-in and webhook steps in README.md, and add all the corresponding values as Worker secrets/variables. No automatic WhatsApp notification can be promised free.

## Persistence and reminder guarantees

Leads and their two notification jobs are written in one D1 batch transaction. Concurrent Worker isolates claim jobs with one atomic conditional UPDATE and write the attempt log in the same transaction. Each claim has a unique token; completion is conditional on that token. A sending job interrupted for more than two minutes becomes `unknown`, never an automatic resend. Cron recovers stale attempts and processes up to one queued notification per invocation. Initial submission starts one notification attempt with `waitUntil` after the durable lead commit. The cron picks up queued work even if that background invocation is interrupted.

The reminder becomes due 168 hours after creation and is attempted on a later scheduled invocation. Done cancels eligible jobs; reopening does not rearm them. Requests already sent/in flight cannot be recalled. Duplicate signed webhook owner commands are deduplicated transactionally, including when a lead has since been reopened. Rate limits use Cloudflare's trusted connecting IP header, hashed before storage, instead of a shared reverse-proxy socket IP.

Limits: low-volume deployment designed for Workers Free CPU, subrequest and database quotas. Polling and due-work batches are deliberately small. Monitor usage and queue backlog. Exact timing during quota exhaustion or provider outages is not guaranteed. The D1 APIs are asynchronous; local tests use a transaction-capable SQLite adapter to test SQL and state transitions. Live Cloudflare runtime and CPU behavior must also be checked after deployment.

## Existing products and enquiries

The new D1 database starts empty. Your local records remain on your computer. Re-enter public products in the hosted admin, or perform a deliberate private migration with compatible column mappings. Never put customer records, database dumps or credentials in the public GitHub repository. Back up the D1 database privately and verify restore procedures.

## Smoke checks

Confirm homepage, `/health`, `/admin` sign-in and product publication. Submit one test enquiry and verify persisted service-specific details, price snapshot and status changes. Check Worker Cron Triggers show the schedule and examine notification history. With WhatsApp disabled, expect blocked sends, not actual messages. Once Meta is configured, test template acceptance, delivery status webhooks and an owner `done UUID` command before relying on reminders.
